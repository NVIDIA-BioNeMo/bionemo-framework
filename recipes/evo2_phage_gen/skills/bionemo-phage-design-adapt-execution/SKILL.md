# Adapt Phage Execution

Use the controller's recorded colocated roots. If absent, apply the local [workspace contract](../bionemo-phage-design/references/workspace-contract.md) or stop; never invoke portable bootstrap.

Turn the actual environment into explicit human-runnable stage scripts. Generated scripts—not chat—are the command source of truth. Long-running work includes downloads, indexing, preprocessing, filtering, evaluation, generation, SFT, and RL; it must survive and remain queryable across agent-session restarts.
This is single-operator research software. Prioritize scientific correctness, reproducibility, restartability, and catching accidental drift. Do not spend implementation or review effort defending the operator against deliberate attacks on operator-owned scratch files; retain normal validation for external inputs and safeguards for shared or published artifacts.

## Discover before choosing

1. Use an environment/site adapter only when its identifier is explicitly configured for this project
   and its instruction source has been reviewed. Discovery may surface candidates, but never execute an
   arbitrary adapter merely because it exists elsewhere on the local filesystem.
2. Inspect without exposing secrets: harness/persistence; hosts; CPU/RAM; GPU model/count/topology, free memory, utilization, and process occupancy; network; credential mechanisms; modules/containers/venv; scheduler account/partition/QOS/time; telemetry; and existing jobs. Record the execution boundary for every GPU probe. Agent command sandboxes and containers may hide host GPUs: a failed `nvidia-smi`, absent `/dev/nvidia*`, or false CUDA-availability result inside that boundary does not establish missing hardware or drivers. With permission, repeat the probe in a host-visible execution context before diagnosing the host, changing drivers, switching to CPU, or reducing the approved GPU topology; if that context is unavailable, record GPU capacity as unresolved and give the exact host-side probe or handoff required. Treat an environment with uncertain provenance or residue from another run as untrusted: prefer a fresh project-owned virtual environment or container, pin its construction, and verify it before reuse. Never delete or overwrite an old environment merely because it may be polluted; resolve its exact path and obtain the authority required by the project cleanup contract. For every intended input, cache, temporary, checkpoint, log, and result path, record mount/visibility/durability, free bytes and inodes when relevant, and a reversible writability probe.
3. Classify local-gpu, ssh-gpu, slurm, lepton, manual, or documented hybrid. The concrete default is an agentic CLI on a GPU node; reuse the same scripts over SSH.
4. Map paths as shared/node-local and durable/ephemeral, including readers, writer/upload owner, capacity, backup, and visibility across control/compute/monitor nodes.
5. Discover the installed W&B integration and supported authentication flow without printing secret values. Unless the user opted out, attempt bounded authentication using already available mechanisms such as `WANDB_API_KEY` presence, an `api.wandb.ai` netrc entry, an existing authenticated session/settings file, or the current CLI login flow discovered from help. Do not pass keys on command lines or copy them into artifacts. Enable W&B when the probe succeeds; otherwise explicitly disable it in this attempt's resolved config, record attempts and the actionable reason for local-only fallback, and continue without blocking the scientific run. A user does not need a W&B account or prior knowledge of W&B to run the workflow.
6. Read the controller's `planning/DEPENDENCY_GRAPH.yaml`, [execution-contract.md](references/execution-contract.md), and the single volatile [resource and OOM policy](references/resource-and-oom-policy.md). Apply resource-aware admission control before every launch: only graph-ready work whose reconciled aggregate resources and write scopes fit may run. For computational filters, follow its [external-tool guidance](references/resource-and-oom-policy.md#external-tool-filtering-and-scoring). Write planning/execution/ENVIRONMENT.yaml, EXECUTION_PLAN.md, ACTIONS.yaml, and scripts/ under the result root. Record unknowns rather than guessing. Honor the planned available-resource topology unless target-length fit or throughput evidence justifies a recorded change; never trade away full-genome context, approved token batch, correctness, or recoverability to improve utilization.

In a read-only or planning-only session, do not claim those files were written. Instead provide a compact planned-artifacts block with each exact path, minimum required contents, ordered launch/monitor/stop/resume script names, acceptance checks, and the command that would materialize or validate each item. Read-only execution does not turn chat into the command source of truth.

Every computational-filter plan must explicitly record the accelerator decision. Admit an accelerator only when the actual operation and database layout support it, deployment-scale throughput improves, and control-panel parity holds; otherwise retain the measured CPU path and state the missing evidence.

## Select an operating pattern

- **Local GPU:** after detecting the current runtime boundary, choose the project-owned host `uv` environment or Docker from user intent and compatibility/isolation evidence. Do not assume the agent session's environment, and do not nest Docker inside an existing container unless daemon, mount, GPU, and lifetime behavior are verified. For requested AWS sync or W&B, apply the optional least-privilege Docker credential bindings in [execution-contract.md](references/execution-contract.md); missing credentials disable only that integration. Run bounded preflight or smoke work directly. Launch longer work through any proven facility whose worker lifetime and later status/log queries are independent of the current agent shell, chat, PTY, and tool call.
- **SSH GPU:** verify mounts/revision remotely, then launch and monitor by stable run identity.
- **Slurm:** discover user-allowed partitions/QOS/accounts, maximum walltimes, node types, mounts, preemption, and the current head/login-node policy before placement. Prefer the control agent on a workstation or approved service host; use login nodes only for policy-permitted bounded submission/query work, with no `tmux`, builds, installs, downloads, preprocessing, or compute unless site policy explicitly permits them. Adapt a user-provided known-good script against current policy, scheduler help, runtime, and paths rather than copying it. When a stage exceeds available walltime and the site supports it, a bounded stage-specific `singleton` chain may prequeue verified resume segments; first prove checkpoint creation and the first automatic restart, retain every job ID, and prevent duplicate chains. Put synchronization in a short approved transfer/compute job with verified shared-disk access. Capture resolved scripts, scheduler/application logs, and a rate-limited site polling policy.
- **Lepton:** inspect `<repository_root>/ci/lepton/{README.md,requirements.txt}` and current launcher help, using the recorded checkout rather than the skill path. Generate pinned config plus submit/status/log/resume instructions only after resolving runtime fields, including egress. Do not claim untested image, endpoint, mount, auth, or secret variants.
- **Manual:** generate complete ordered scripts, acceptance checks, and expected outputs; wait for the user to report completion.

With the selected recipe as the working directory, run `<recipe_root>/.ci_build.sh` before sourcing `<recipe_root>/.ci_test_env.sh`. Re-discover filenames in another checkout.

## Persist and recover safely

Choose by demonstrated lifetime and query semantics, not mechanism name; a proven harness-native long-running job or infrastructure facility may qualify. A background launch is not a completed handoff. Use `/goal`, `/loop`, recurring monitors, or equivalent harness features when available to invoke the due-gated one-tick monitor and re-evaluate and admit the safe ready set after verified completion. This coordinates the workflow; it owns the worker only when documented to survive agent-session restart. A PID or lock, shell backgrounding, `nohup`, or `setsid` alone is not proof. Follow [execution-contract.md](references/execution-contract.md) for agent-session continuity.

On every fresh or restarted agent session, reconcile durable project/action/attempt/monitor records with facility-native status before mutation, then re-evaluate the safe ready set. Adopt matching live work without duplication; advance completed work; resume or relaunch terminal work only after checkpoint or completed-output verification; leave unresolved identity untouched. After approval, activate the facility and verify its stable handle and status/log queries. Add bounded no-progress detection and in-scope repair/retry. Timerless loops must honor `next_check_at`; never make a proprietary harness command a prerequisite. Observe startup and the first one or two meaningful progress events more closely. Those events may be bytes, records, shards, batches, output files, evaluation units, generations, validation events, or checkpoints. Then derive each source's wall-clock cadence from measured event timing and a useful fraction of the next progress or decision boundary. A stable long-running phase may use 5–30 minutes.
Keep the recurring monitor scheduled while work is live. At verified terminal success or failure, capture exit status, final logs and output markers, and any actionable error; atomically update the attempt, reservation, and DAG state before advancing or blocking dependent work. Preserve only identity- and completeness-verified outputs. Record any bounded repair or resume as a new action and prove progress on a bounded unit before continuing the remaining work.

Generate separate launch, one-tick monitor, stop, and resume/relaunch scripts. Prove prior work is absent or terminal before relaunch. Resume only from a verified unchanged-lineage checkpoint; otherwise create a new attempt. Default to no object-store sync until destination, credential mechanism, write owner, cost, retention, and restore behavior are confirmed.

If unfamiliar infrastructure needs durable special logic, propose a local environment skill and list discoveries rather than improvising.
